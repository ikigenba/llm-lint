# Decision 8 — Reporting, formats, and exit computation

**Decision.** Package `internal/report`.

```go
func Text(w io.Writer, cwd, root string, findings []engine.Finding) error
func JSON(w io.Writer, findings []engine.Finding) error
func StatsLine(w io.Writer, s Stats) // stderr, only with --stats

// VerboseSink streams the --verbose progress trace live to w (stderr), one line
// per judged (rule, file) pair, the moment each pair's verdict is known. It
// implements engine.TraceSink (D05); run injects it into the caching client
// (D06), which calls Add from its workers. Concurrent Add calls are serialized
// so a line is never interleaved with another. Each line reports only the
// pass/fail verdict (from TraceEntry.Outcome); TraceEntry.Cached is ignored.
// Only with --verbose.
type VerboseSink struct { /* w io.Writer; cwd, root string; mu sync.Mutex */ }

func NewVerboseSink(w io.Writer, cwd, root string) *VerboseSink
func (s *VerboseSink) Add(e engine.TraceEntry)

type Stats struct {
    Rules, Files, Pairs, Calls, CacheHits int
    InputTokens, OutputTokens             int64
    CostUSD                               float64
}
```

Findings are sorted deterministically before rendering — by (file, line,
rule) — so concurrent completion order never changes output. Text format, one
finding per line on stdout, paths relative to the invoker's cwd:

    <path>:<line>: <explanation> (<rule-id>)

Warnings and errors render identically (severity's only role is exit-code
computation); a clean run writes nothing to stdout. `--format json` instead
emits a JSON array (empty array when clean) of objects with exactly the keys
`rule`, `severity`, `file`, `line`, `evidence`, `explanation` — `evidence`
being the exact source line text (D05 guarantees it), which is what lets a
downstream consumer construct a stable finding identity; llm-lint itself
computes none. Exit computation (used by D01): any error-severity finding →
1; findings but all warnings → 0.

`StatsLine` writes a single human line to stderr after the run:

    llm-lint: 2 rules, 41 files, 82 pairs, 7 calls, 75 cache hits, 118k in / 2k out tokens, $0.0113

`VerboseSink` streams the `--verbose` progress trace to stderr live as the run
proceeds, independent of `--format` (findings still render to stdout in the
chosen format). Each judged (rule, file) pair produces one line the moment its
verdict is known, in the order pairs complete — no end-of-run buffering and no
sort, so under concurrency the lines land in completion order. Each renders on
one line: a pass/fail circle, the path relative to the invoker's cwd, then the
rule id, single-space-separated with no colon:

    <circle> <path> <rule-id>

`<circle>` is the emoji 🟢 when the pair passed (`Outcome == "pass"`) and 🔴 when
it failed (`Outcome == "fail"`); the color is intrinsic to the glyph, so there
is no TTY detection and no `NO_COLOR` handling — the same bytes go to a terminal
or a pipe. `TraceEntry.Cached` is not rendered. Lines carry no `llm-lint:`
prefix — the trace is many lines meant to be grepped and, if the reader wants
order, piped through `sort`. Because workers judge pairs concurrently, `Add`
holds a mutex across its write so a line is never interleaved with another; a
write error on the progress stream is swallowed (best effort) and never fails
the lint. The rendering and non-interleaving are proven end-to-end through the
composition root by D01's `R-H1KL-BCFY`.

Diagnostics (skip warnings, no-rules warning, operational errors) always go
to stderr; stdout carries findings only, so pipes stay clean.

**Rejected.** SARIF or checkstyle formats: no consumer in the settled scope;
the JSON format carries everything needed and more formats are cheap to add
later behind `--format`. A minted stable finding id in the JSON: the
adjudication problem belongs to the build loop (settled during grilling);
emitting exact `evidence` preserves the capability without owning it.
Severity prefixes in text output: `go vet`-family output carries none and
the rule id suffix already identifies the rule. A buffered, sorted end-of-run
trace dump (the previous shape): it hid all progress until the run finished and
printed nothing at all when a run aborted mid-way; streaming each verdict live
gives progress and partial-failure visibility, and the reader can still `sort`
the output when deterministic order is wanted — worth trading the built-in sort
for. A cache hit/miss column on the verbose line (the previous shape carried
`<hit|miss>`): the pass/fail verdict is what a reader scans a progress trace
for, and the cache datum cluttered every line for a signal `--stats` already
totals; dropped. ANSI-colored `●` with TTY/`NO_COLOR` handling for the verdict:
the trace is a human progress view on stderr, not a machine contract (findings
on stdout are), so the color-stripping branch and its tests earn nothing here;
the emoji 🟢/🔴 carry their own color and keep the sink branch-free.

**Verification.**

- R-HDNX-RNLN — text output renders `<path>:<line>: <explanation>
  (<rule-id>)` with the path relative to the invoking cwd (verified from a
  subdirectory of Root).
- R-HEVU-5FCC — JSON output is a valid array of objects with exactly the
  keys rule, severity, file, line, evidence, explanation, and `evidence`
  equals the flagged line's exact text; a clean run emits `[]`.
- R-HG3Q-J731 — `--stats` writes the one-line summary to stderr and nothing
  extra to stdout; with a fake Client reporting non-zero per-call usage the
  line's input-token, output-token, and cost figures are the run's non-zero
  totals (not the zero placeholders), and without the flag the line is absent.
- R-HHBM-WYTQ — findings supplied out of order render sorted by (file, line,
  rule) in both formats.
