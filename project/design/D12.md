# Decision 12 — Built-in rule: boolean-state-machine

**Decision.** The built-in catalog includes
`internal/rules/builtin/boolean-state-machine.md`:

- `description`: multiple booleans encoding one multi-state concept that
  should be a single enum
- `severity`: `error`
- `include`: omitted — the rule targets code generally, so it takes
  `rules.DefaultCodeGlobs` (D03) by mechanism, never by copying the list
- `exclude`: none (the anti-pattern is as real in test code as anywhere, and
  a state-carrying declaration can live in any file)

The prompt body is language-agnostic: flag a group of two or more boolean
fields, variables, or columns that together represent one concept with more
than two states, where some combinations of the booleans are invalid or
meaningless. The tell is mutual dependence — setting one flag true forces
another false, or one state change must write several flags together. The
body anchors on the ticket example (open/held/sold stored as `held` and
`sold`, where `held && sold` is meaningless, so the pair is really one
three-state value that should be a single enum or status field). It
explicitly spares: genuinely independent booleans where every combination is
a valid state (e.g. `isAdmin` and `emailVerified`); a single boolean;
booleans derived on the fly from one source of truth (e.g.
`done := status == StatusDone`); and bit flags in an established
flags/bitmask type. The body includes one short flagged and one short spared
example to anchor the judgment. Exact prompt wording is the build loop's to
write and tune within this frame.

This rule is active by default like every rule in the catalog (D03); a
project silences it with `disable: ["boolean-state-machine"]`. It is
deliberately **not** added to the repo's own self-lint gate config (D11)
until its prompt has been tuned against real trees.

**Rejected.** A syntactic multiple-bools-in-a-struct trigger: two booleans in
one struct are usually legitimate independent flags; the discriminator is
whether invalid combinations exist, which is exactly the judgment call an
inference rule can make and a parser cannot. A dedicated live-model efficacy
test for this rule: D05's live ids already prove the engine-to-provider path
end-to-end, and a cheap model's per-rule verdict on a fixture is not
deterministic enough to be a reproducible exit condition; prompt efficacy is
tuning work, not a gate. Test-file excludes: nothing about test code makes
the anti-pattern acceptable there.

**Verification.**

- R-4IQ0-3CA4 — the embedded catalog contains a rule with id
  `boolean-state-machine`, severity error, `Include` equal to
  `rules.DefaultCodeGlobs`, no excludes, and a prompt whose guidance is
  anchored on invalid boolean combinations (contains both the invalid-
  combination criterion and the ticket held/sold example); it appears in
  `--list-rules` output.
